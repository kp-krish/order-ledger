# Order Ledger implementation plan

## Goal

Build a production-shaped inventory projection service that consumes `order.placed`,
`order.cancelled`, and `order.shipped` events from Kafka, applies them exactly once
at the database boundary, exposes the resulting state over REST, and demonstrates
the failure modes that motivated its concurrency controls.

## Architecture decisions

- Java 21 and Spring Boot 4.1.1, built with Maven Wrapper.
- PostgreSQL is the source of truth for the materialized inventory and order views.
- Kafka topic `orders.events` starts with one partition and can be raised to three.
- Producers key records by `orderId`; consumers still enforce a monotonically
  increasing per-order sequence number because replays and incorrect producers can
  violate broker ordering assumptions.
- `processed_events.event_id` is inserted in the same database transaction as the
  state mutation. Its primary key is the idempotency gate.
- All inventory rows affected by one event are locked in lexicographic SKU order to
  prevent opposite-order deadlocks.
- Oversells are recorded explicitly instead of allowing negative available stock to
  disappear as an implementation detail.
- JSON event payloads are versioned and validated at the consumer boundary.

## Delivery stages

1. Repository isolation and documented plan.
2. Spring Boot/Maven scaffold, local infrastructure, health checks, and CI skeleton.
3. Flyway schema and event contract.
4. Transactional processor with idempotency, sequencing, and deterministic locks.
5. Kafka listener, retry/error behavior, and REST query API.
6. Synthetic producer with duplicates and out-of-order scenarios.
7. Testcontainers integration coverage for duplicate delivery, stale ordering,
   consumer restart, and concurrent multi-SKU processing.
8. Metrics, benchmark/lag-recovery tooling, runbook, and architecture documentation.
9. Full verification and repository review.

Each stage is committed separately and pushed after a GitHub remote is available.

## Required acceptance tests

- Replaying the same event ID does not double-apply inventory changes.
- A lower or equal sequence for an order is rejected as stale without state changes.
- Restarting the consumer during a workload loses no accepted event and double
  applies none.
- Concurrent orders that touch the same SKUs complete without lock-order deadlocks.
- `GET /inventory/{sku}` and `GET /orders/{id}` return the current projection and
  return `404` for unknown resources.

## Evidence to publish

- Sustained events per second on the test machine.
- Duplicate rejection count for a documented replay size.
- Integration-test count and JaCoCo line coverage.
- Consumer-lag recovery time after a controlled restart.

Machine-specific values will be generated by scripts and recorded only after they
have actually been measured; the README will not claim invented results.
